# Pi 房间

`oai` 插件可以把任意房间接到本机 Pi CLI，鉴权与工具沿用 Pi 自身配置。

引擎是房间自己的属性，与名字无关：

| 指令 | 效果 |
| --- | --- |
| `##研究 pi` | 新建一间 Pi 房间，模型沿用 Pi 自身配置 |
| `##研究 pi/apilio/claude-opus-5` | 新建并指定模型 |
| `研究%pi` | 把已有房间转成 Pi 房间 |
| `研究%pi apilio/kimi-k3` | 换这间房用的 Pi 模型 |
| `研究%gpt-5.6-luna` | 转回中转站房间 |

`pi` 后面用空格、`/` 或 `:` 分隔模型都可以，大小写不限，房间名不受限制。

## 供应商与思考强度

普通（中转站）房间的模型可以写成 `供应商/模型`，按供应商路由到不同接口：

| 指令 | 效果 |
| --- | --- |
| `##助手 deepseek/deepseek-flash` | 建一间走 DeepSeek 官方接口的房间 |
| `助手%apilio/gpt-5.6-luna` | 换回 apilio 中转站 |
| `助手%deepseek/deepseek-flash:high` | 换模型并顺带设思考强度 |
| `##助手 deepseek/deepseek-flash:low` | 建房时直接指定强度 |

供应商在 `[oai.providers]` 里定义（`api_base` + `api_key`）。`apilio` 是历史默认接口，即使不单独配置也始终回退到 `[oai]` 那一份（`oai <url> <key>` 配的），无需重复填写；未知供应商会明确报错，不会悄悄打到别的站点。不带前缀的模型仍走默认接口，行为不变。

思考强度取 `off` / `minimal` / `low` / `medium` / `high`（`xhigh` 也认），有两种写法：模型后的 `:强度` 后缀优先，其次是房间自己的 `thinking` 字段。Pi 房间把强度交给 `pi --thinking`，普通房间转成请求里的 `reasoning_effort`，留空表示交给引擎默认。`/#` 与回执里会标出 `· 思考:强度`。

早先只有名为 `pi` 或 `pi-*` 的房间才能用 Pi，于是所有想用 Pi 的房间都被迫顶着这个前缀。现在引擎写在房间自己身上（配置里的 `engine` 字段），首次启动时按当初的名字规则一次性写好，已有房间的行为不变，此后名字改成什么都不影响引擎。`-` 仍不能出现在新房间名里（`助手-1` 是「删除第 1 条」的写法），历史上的 `pi-*` 房间是唯一例外，继续放行。

## 行为

- 公有、私有、临时三种模式各自隔离会话；改写历史或重新生成会重建对应的 Pi 会话
- 房间模型即 Pi 的 `--model`，支持 `provider/id` 与 `id:thinking` 写法（如 `apilio/gemini-3.8-flash:low`），也接受裸 id 由 Pi 自己找 provider。留空则沿用 Pi 自身配置，`/#` 与卡片页脚显示「Pi · 本机配置」，指定了模型则显示「Pi · 模型名」
- 中转站在售的模型可以一次性登记进 Pi，见下文「中转站模型」
- 房间提示词追加到 Pi 的系统提示词之后
- 正文经 stdin 传入，图片写入临时文件传入，调用结束后清理；中间思考与工具输出不写入聊天记录
- 回复卡片页脚显示实际模型、耗时与工具调用轨迹；不含标题、列表或代码块的短回复直接发文本，不渲染图片
- 停止或超时会终止 Pi 及其调用树内的工具进程，包括 Pi 通过 bash 派生的独立进程组
- CLI 启动失败或非零退出作为对话失败返回，不影响其他房间

## 配置

位于 `config.toml` 的 `[oai]` 段：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `pi_command` | `pi` | Pi 可执行文件路径或命令 |
| `request_timeout_seconds` | `300` | 单次回复的总时间预算 |
| `pi_stall_seconds` | `90` | 事件流静默这么久算卡死；卡住且没出正文时自动重来一次，`0` 关闭 |
| `plain_text_max_chars` | `120` | 短回复的纯文本阈值，`0` 表示始终渲染图片 |
| `show_trace_footer` | `true` | 是否在卡片页脚显示模型、耗时与工具轨迹 |
| `providers` | 空 | 供应商表，每项含 `api_base` 与 `api_key` |

Pi 自己不给模型请求设超时：上游抽风时它会安静地卡在网络等待上，直到总预算耗尽（实测 5 分钟墙钟只烧 2 秒 CPU）。事件流是它还活着的证据，所以静默超过 `pi_stall_seconds` 就掐掉重来一次；已经吐出正文之后再卡，则直接把已有的交出去。

鉴权与工具在 Pi 侧配置，不经由 ayjx；模型由房间指定。卡片渲染依赖 Chrome/Chromium，渲染失败时回退纯文本。等待期间不发进度提示——一条播报换不来更快的回复，只会在群里插进一段与上下文无关的噪音。

## 中转站模型

Pi 房间可以直接写中转站的模型 id。未登记的 id 照样发得出去，但 Pi 只能对它套用默认的上下文窗口、输出上限与「纯文本」模态，发图的房间会悄悄丢掉图片，长对话在真正超限之前就被压缩。登记一次这些账就都算得准了：

```sh
python3 scripts/sync-pi-models.py --dry-run   # 先看要写什么
python3 scripts/sync-pi-models.py             # 写入 ~/.pi/agent/models.json
```

名单沿用 `[oai].model_filter`，`/%` 看到的和 Pi 房间能选的是同一批。中转站上新或下架时只改 `config.toml` 里的那一处，然后重跑脚本。识图能力是逐个模型实测出来的——中转站自己的标签并不可靠，曾把 Claude Sonnet 5 标成纯文本——`--probe` 会重新实测一遍。脚本只覆盖 `models.json` 里 `apilio` 这一个 provider 的 `models` 数组，写前自动备份，不动密钥、`settings.json` 或其它 provider。

发起人是 `ctl.admins` 里的管理员时，这一轮对话还可以用自然语言操作机器人自身的插件开关与配置，见[插件控制](CONTROL.md#在-pi-房间里用自然语言操作)。

同一个 Pi Agent 还可以作为群成员之一旁听群聊、偶尔搭话，见[群聊搭话](ambient.md)。
